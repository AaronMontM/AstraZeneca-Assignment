# Finance Spend Intelligence Assistant

An AI-powered finance assistant for exploring company spending, investigating invoices and identifying potential procurement policy compliance issues.

The application combines a conversational interface with deterministic data tools, procurement policy context and financial dashboards. It is designed to help Finance users obtain useful answers from structured invoice data while retaining visibility into the information supporting those answers.

## 2. Architecture and Implementation Decisions

### Data preparation

The original invoice files are consolidated into an enriched dataset containing the financial and procurement information required by the application.

The preprocessing stage includes:

- Consolidating the provided invoice sources.
- Normalising and enriching invoice attributes.
- Converting non-EUR amounts into EUR using the provided ECB 2025 exchange rates.
- Handling missing exchange-rate dates using the nearest available previous rate, where applicable.
- Adding temporal attributes to support date-based analysis.
- Preparing the data required for procurement policy checks and financial summaries.

The resulting dataset is stored as a processed CSV file and loaded by the backend.

Pandas was chosen because the assignment dataset is relatively small (140 invoices). A distributed processing framework would add unnecessary complexity at this stage.

### Backend and agentic routing

The backend is built with FastAPI and exposes endpoints for the assistant, configuration, financial summaries, dashboards, invoice exploration, usage information and conversation history.

The LLM is responsible for interpreting user intent and selecting the appropriate route and tools. The application separates routing decisions from answer generation:

- **Routing:** The model's thinking capability is enabled to interpret the user's request, determine the appropriate route and select the required tools.
- **Answer generation:** Thinking mode is disabled. Instead, the backend executes the selected operations deterministically and provides their structured results, together with the relevant procurement policy context, to the LLM to formulate the final response.

This separation keeps financial calculations and data retrieval under backend control, while using the LLM to interpret requests and communicate the results in natural language.

The routing layer uses structured decisions and validation to ensure that model outputs conform to the expected routing schema. A retry mechanism is available when a routing decision cannot be successfully parsed or validated.

#### Deterministic tools

The assistant uses dedicated backend tools to retrieve and process financial information:

| Tool | Purpose |
|---|---|
| `search_invoices` | Search invoices using filters such as vendor, status, currency, cost centre, invoice date and EUR amount. |
| `get_invoice_details` | Retrieve detailed information about a specific invoice. |
| `get_spend_summary` | Calculate spending totals and breakdowns. |
| `get_compliance_overview` | Retrieve procurement compliance indicators and supporting information. |

Financial calculations and data retrieval are performed by the backend rather than delegated to the LLM. This improves consistency and reduces the risk of numerical hallucinations.

#### Guardrails

The current guardrail implementation focuses on two responsibilities:

- **RoutingGuardrail:** Handles `OUT_OF_SCOPE` decisions by returning a predefined response explaining the assistant's scope, and handles `CLARIFICATION` decisions by returning the clarification question generated by the router.
- **AnswerGuardrail:** Checks that the LLM response is not empty and returns the trimmed answer. Empty responses raise an error.

These checks provide basic protection against unsupported request categories and empty model responses. They are not intended to replace a comprehensive production validation, security or hallucination-detection layer.

The procurement policy is provided as contextual information to the LLM when relevant. The current implementation does not require a dedicated vector database or a full RAG pipeline.

## 3. Evaluation Approach and Results

The evaluation framework was designed to measure both functional reliability and answer quality.

A benchmark of 100 initial scenarios was created, with 20 cases for each of the five routing paths. An additional 20 follow-up interactions were included to test conversation continuity, resulting in 120 evaluated turns.

Four generation models were compared:

- `gemma4:12b`
- `llama3.1:8b`
- `mistral-nemo:12b`
- `qwen3.5:9b`

A separate LLM judge (`gpt-oss:20b`) was used to assess answer quality.

The four models were selected following preliminary tests in the local development environment. Only models achieving an average response latency below 15 seconds during these tests were shortlisted for the comparative evaluation.

This threshold was used as a practical selection criterion based on the available hardware (AMD Ryzen AI 7 350, 32GB RAM, NVIDIA GeForce RTX 5070 8 GB GDDR7) and development constraints, rather than as a general performance benchmark.

### Evaluation metrics

| Metric | Evaluation approach |
|---|---|
| Route accuracy | Deterministic comparison against the expected route. |
| Data retrieval accuracy | Deterministic comparison between retrieved data and expected results. |
| Policy answer accuracy | LLM-based assessment against reference answers. |
| Both answer accuracy | LLM-based assessment for questions requiring data and policy context. |
| Clarification accuracy | Deterministic assessment of whether clarification was correctly triggered and handled. |
| Factual correctness | LLM-based assessment of factual claims. |
| Faithfulness | LLM-based assessment of consistency with the available evidence. |
| Answer relevancy | LLM-based assessment of relevance to the user's question. |
| Context precision | LLM-based assessment of the relevance of the retrieved context. |
| Context recall | LLM-based assessment of whether the available context contains the information required by the reference answer. |

Average response latency is also recorded to compare performance.

The evaluation combines deterministic metrics, which are preferable for objective checks, with LLM-based assessment for dimensions that require semantic judgement.

### Model comparison

The following table summarises the results obtained with the four models:

| Model | Route accuracy | Data retrieval accuracy | Policy answer accuracy | Both answer accuracy | Clarification accuracy | Factual correctness | Faithfulness | Answer relevancy | Context precision | Context recall | Avg. latency |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| **Gemma 4 12B** | 91.67% | 76.37% | 98.96% | 72.92% | 85.00% | 88.12% | 90.81% | 88.75% | 88.93% | 83.04% | 14.78s |
| **Llama 3.1 8B** | 79.17% | 67.72% | 92.71% | 63.54% | 15.00% | 69.69% | 75.00% | 80.62% | 89.64% | 76.16% | 3.69s |
| **Mistral Nemo 12B** | 63.33% | 76.61% | 89.58% | 56.25% | 15.00% | 75.31% | 81.06% | 86.56% | 87.50% | 76.07% | 12.17s |
| **Qwen 3.5 9B** | 83.33% | 75.96% | 100.00% | 76.04% | 65.00% | 86.75% | 90.19% | 89.06% | 92.68% | 83.12% | 4.93s |

Gemma 4 12B achieved the strongest overall functional performance, particularly in routing and clarification handling, as well as strong answer-quality scores. Qwen 3.5 9B offered a competitive alternative, with the highest policy answer accuracy, strong retrieval and answer-quality results, and substantially lower latency.

The results illustrate the trade-off between response time and answer quality. The preferred model for production would ultimately depend on workload, concurrency, quality thresholds and inference costs.

The judge is not treated as an unquestionable source of truth. In a production evaluation process, its results should be calibrated against human assessments and reviewed for consistency.

## 4. Installation and Execution

### Prerequisites

- Python 3.11 or compatible version.
- Node.js and npm.
- Docker and Docker Compose.
- Ollama, with at least one supported model downloaded.

### 1. Clone the repository

```bash
git clone https://github.com/AaronMontM/AstraZeneca-Assignment.git
cd AstraZeneca-Assignment
```

### 2. Configure environment variables

Create the root `.env` file using the provided example:

```bash
cp .env.example .env
```

Review the configuration and adjust the database, API and LLM settings if necessary.

### 3. Start the database

```bash
docker compose up -d db
```

Wait until PostgreSQL reports a healthy status.

### 4. Start the backend

From the `backend` directory, install the dependencies using the project's dependency manifest.

```bash
python -m pip install -r requirements.txt
```

Then start the API:

```bash
uvicorn app.main:app --reload
```

The API is available at:

```text
http://localhost:8000
```

Interactive documentation:

```text
http://localhost:8000/docs
```

### 5. Start the frontend

From the `frontend` directory:

```bash
npm install
npm run dev
```

The frontend is available at:

```text
http://localhost:3000
```

### 6. Start Ollama

Make sure Ollama is running and that the model configured in `.env` is available locally.

For example:

```bash
ollama pull qwen3.5:9b
```

The generation model can be changed through the application configuration.

## 5. Production Considerations

The current implementation is a functional prototype built around the dataset and constraints of the assignment. Deploying it for approximately 200 Finance users and real financial data would require additional work in several areas.

### Data platform and scalability

The current Pandas-based preprocessing and CSV storage are sufficient for 140 invoices, but I would evolve the data layer as the volume and number of data sources increase.

Potential improvements include:

- **CSV to Parquet:** Store processed analytical data in Parquet to reduce storage requirements and improve column-oriented reads.
- **Pandas to PySpark:** Introduce PySpark if data volume, transformation complexity or processing requirements justify distributed execution. For moderate volumes, Pandas or a database-backed approach may remain more efficient.
- **Automated ingestion:** Replace manual file preparation with scheduled or event-driven ingestion pipelines from ERP, procurement and finance systems.
- **Data validation:** Introduce schema checks, reconciliation against source systems, duplicate detection and data quality monitoring.
- **Incremental processing:** Process new and updated invoices rather than rebuilding the complete dataset every time.
- **Data versioning and lineage:** Keep track of source files, transformation versions, exchange rates and processing dates.
- **Evolving data and tools:** When new data sources or business requirements are introduced, extend the preprocessing pipeline and the deterministic toolset to make the additional information available to the assistant.

For production, I would also consider separating the analytical data layer from the transactional application database. PostgreSQL could continue to manage conversations, configuration and audit metadata, while a suitable analytical storage or warehouse platform could serve larger financial datasets.

### Access control and identity management

A production deployment should integrate with the organisation's identity provider and support:

- Enterprise SSO.
- Role-based access control (RBAC).
- Permissions based on Finance roles, business units, legal entities or cost centres.
- Row-level restrictions where users should only access specific financial records.
- Least-privilege service accounts and database permissions.
- Session management and controlled access to conversation history.

The backend must enforce permissions independently of the LLM. A model-generated routing decision must never determine whether a user is authorised to access a record.

### Audit trails and governance

Auditability is particularly important for financial applications.

The implementation should be extended to record the information required by procurement policy §8.2 and the organisation's audit requirements.

An audit trail should capture, at a minimum:

- User identity and timestamp.
- User question and conversation reference.
- Model and model version.
- Routing decision and selected tools.
- Tool arguments and execution results or references to them.
- Data sources and evidence used to produce the answer.
- Final response and relevant policy version.
- Errors, retries and changes to application configuration.

Audit records should be tamper-resistant, access-controlled and retained according to the organisation's retention policy.

Sensitive information should be handled carefully: logging should not unnecessarily duplicate confidential invoice data or personal information. Access to audit records should itself be audited.

### Security and infrastructure

Before production, I would add:

- Encryption in transit and at rest.
- Centralised secret management instead of local environment files.
- Network isolation and restricted database access.
- API authentication, authorisation, rate limiting and input validation.
- Dependency and container vulnerability scanning.
- Secure CI/CD pipelines and separate development, staging and production environments.
- Database backups, recovery procedures and high availability.
- Monitoring for API availability, latency, errors and resource consumption.

### LLM reliability and cost management

Serving 200 Finance users requires a deliberate model deployment strategy.

I would assess managed LLM services versus dedicated self-hosted inference based on data residency, security, latency, throughput and total cost of ownership.

The production setup should include:

- Load testing with realistic concurrent usage.
- Request queues and concurrency limits.
- Token and request budgets per user or department.
- Model selection based on task complexity.
- Caching for repeatable, non-sensitive queries where appropriate.
- Monitoring of token consumption, latency and inference costs.
- Fallback behaviour when the model or inference service is unavailable.

For numerical and financial operations, deterministic backend calculations should remain the source of truth.

### Evaluation and continuous improvement

The benchmark should become a maintained regression suite, expanded with real-world questions and edge cases.

I would introduce:

- Human-reviewed reference datasets.
- Regular regression tests after prompt, model or tool changes.
- Evaluation of retrieval and evidence quality.
- Monitoring of hallucinations and unsupported claims.
- User feedback and expert review of problematic answers.
- Model and prompt version tracking.
- Release thresholds for factual accuracy, routing reliability, latency and cost.

If a dedicated RAG or document retrieval pipeline is introduced in the future, frameworks such as RAGAS could help evaluate retrieval and generation quality. The current implementation primarily uses deterministic tools and directly supplied policy context, so introducing a full RAG evaluation framework was not a priority for this assignment.

### Internationalisation

The application could be extended to support multiple languages, allowing Finance users from different countries or business units to interact with the assistant in their preferred language.

This would require multilingual prompts, consistent language handling across the interface and generated responses, and evaluation benchmarks covering each supported language.

## 6. Scope and Priorities

The objective was to deliver a working end-to-end prototype rather than a production-scale financial platform.

The main priorities were:

1. **Reliable financial operations:** Keep calculations and data retrieval deterministic and separate from LLM reasoning.
2. **Controlled agent behaviour:** Implement explicit routing, validation, clarification and out-of-scope handling.
3. **Usable financial exploration:** Provide both a conversational interface and complementary dashboard and invoice views.
4. **Measurable quality:** Build a benchmark that evaluates routing, retrieval, answer quality and latency across different models.

Some production capabilities were deliberately left out, including enterprise SSO, granular access control, immutable audit infrastructure, automated ingestion from financial systems, distributed data processing and a full RAG pipeline.

These were excluded to prioritise a working solution and a meaningful evaluation within the assignment's time constraints. They are part of the proposed production roadmap rather than capabilities the prototype currently claims to provide.
